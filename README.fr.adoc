= deploy
:toc: left
:toc-title: Table des matières
:toclevels: 3
:source-highlighter: rouge
:icons: font

Shard Crystal pour le déploiement d'applications https://martenframework.com[Marten] et https://kemalcr.com[Kemal] sur serveurs FreeBSD.
Style Capistrano : `releases/`, `current/`, `shared/`.
Génère dynamiquement les scripts `rc.d` et `nginx.conf`.

== Fonctionnalités

* Déploiement SSH depuis votre terminal local — aucune dépendance côté serveur
* Support natif **Marten** et **Kemal** via le champ `framework` dans `deploy.yml`
* Structure Capistrano : `releases/`, `current/`, `shared/`
* Génération dynamique du script `rc.d` FreeBSD (avec `daemon(8)`, redémarrage automatique et dépendance `REQUIRE: postgresql`)
* Génération dynamique du `nginx.conf` (mode pkg FreeBSD ou Passenger dans `/opt`) avec **pages d'erreur personnalisées** (502/503/504)
* Dialogue interactif pour construire le `.env` lors de l'initialisation
* Création automatique de l'utilisateur PostgreSQL et de la base de données
* Création du CNAME OVH ou Gandi via l'API REST (clés lues depuis le `.env`)
* Rollback en une commande (avec ré-application des migrations Marten)
* Conservation des N dernières releases (configurable)
* Compilation Crystal dans une session `tmux` (résistante aux coupures SSH)
* Génération automatique du workflow GitHub Actions (CI/CD) via `generate-ci`
* **Arrêt gracieux** (zero-downtime) : SIGTERM + attente de fin des requêtes avant bascule
* **Détection automatique de l'environnement** depuis la branche git courante
* **Crontab automatique** : installation idempotente depuis `config/cron/crontab`
* **Déploiement parallélisé** : migrations, assets et crontab s'exécutent pendant la compilation

== Installation

Ajoutez le shard dans votre `shard.yml` :

[source,yaml]
----
dependencies:
  deploy:
    github: aloli-crystal/deploy
    branch: main

targets:
  deploy:
    main: lib/deploy/src/deploy.cr
----

Puis compilez le binaire `deploy` :

[source,sh]
----
shards install
shards build deploy
----

NOTE: Le binaire `deploy` doit être compilé dans votre projet (pas dans le shard). Il lit `config/deploy.yml` depuis le répertoire courant.

== Configuration

Copiez le fichier d'exemple dans votre projet :

[source,sh]
----
cp lib/deploy/examples/marten/config/deploy.yml config/deploy.yml
----

Puis adaptez `config/deploy.yml` :

[source,yaml]
----
app_name: mon-app                              # <1>
repo_url: git@github.com:user/mon-app.git
crystal_main: src/server.cr
keep_releases: 10
framework: marten                              # <2>
database: postgresql                           # <3>

dns:                                           # <4>
  registrar: ovh
  zone: example.app

env_vars:
  required:
    - key: SECRET_KEY
      secret: true
      generate: hex64

environments:
  staging:
    branch: staging
    host: staging.example.com
    user: deploy
    app_url: https://staging.mon-app.example.app
    dns_subdomain: staging.mon-app             # <5>
    dns_target: staging.example.com.

  production:
    branch: production
    host: prod.example.com
    user: deploy
    app_url: https://mon-app.example.app
----
<1> Utilisé pour nommer les répertoires, services et binaires : `mon-app--staging`
<2> Valeurs acceptées : `marten` ou `kemal`. Adapte NGINX, migrations, CI et variables `.env`
<3> Adaptateur de base de données : `postgresql`, `mariadb`, `sqlite` ou `none`
<4> Registrar DNS (optionnel) : `ovh` ou `gandi`
<5> Optionnel — nécessite les clés API du registrar dans votre `.env` local

== Commandes

[source,sh]
----
bin/deploy init --staging       # Initialisation du serveur (une seule fois)
bin/deploy deploy --staging     # Déploiement d'une nouvelle release
bin/deploy deploy --production  # Déploiement en production
bin/deploy rollback --staging   # Retour à la release précédente
bin/deploy status --staging     # Version active et releases disponibles
bin/deploy generate-ci          # Générer le workflow GitHub Actions
bin/deploy dns-setup --staging  # Configurer les clés DNS (OVH / Gandi)
----

=== Détection automatique de l'environnement

Sans `--<env>`, la branche git courante est utilisée pour déduire l'environnement :

[source,sh]
----
git checkout staging
bin/deploy deploy               # → déploie staging automatiquement

git checkout production
bin/deploy deploy               # → déploie production automatiquement
----

La correspondance se fait via le champ `branch` de chaque environnement dans `config/deploy.yml`.

=== Raccourcis par préfixe

Les noms d'environnement peuvent être abrégés :

[source,sh]
----
bin/deploy deploy --stag        # → staging
bin/deploy deploy --prod        # → production
----

== Support Marten vs Kemal

Le champ `framework` dans `config/deploy.yml` adapte automatiquement le comportement :

[cols="2,3,3"]
|===
| Comportement | `framework: kemal` | `framework: marten`

| Variables `.env` NGINX
| `APP_URL` + `UNIX_SOCKET`
| `MARTEN_ALLOWED_HOSTS` + `MARTEN_SOCKET`

| Assets NGINX
| `/css/`, `/js/`, `/images/`, `/vendor/`
| `/assets/` → `public/assets/`

| Migrations
| `db/schema_pg.sql` à l'init
| `bin/marten migrate` avant chaque activation

| Rollback migrations
| Non applicable
| `bin/marten migrate` sur la release précédente

| Tests CI
| `DATABASE_URL` + `schema_pg.sql`
| `DB_*` + `MARTEN_ENV=test` + `marten migrate`

| Seed
| —
| `bin/marten seed` (si commande présente)

| Crontab
| Substitution `sed` + `crontab(1)`
| `bin/marten install_cron` (idempotent)
|===

== Flow de déploiement

Le déploiement est optimisé pour minimiser le temps d'indisponibilité.
Les étapes qui utilisent `bin/marten` s'exécutent en parallèle avec la compilation du binaire applicatif :

[source]
----
clone_repo
link_shared
shards_prepare              ← bin/marten disponible (~15s)
compile_start               ← crystal build --release en arrière-plan (~200s)
  ├── run_migrations        ┐
  ├── run_seed              │ en parallèle avec la compilation
  ├── collect_assets        │
  └── install_crontab       ┘
compile_wait                ← synchronisation
activate_release            ← ln -sf → zero downtime
init_rcd
generate_env_exports
generate_wrapper
start_service
reload_nginx
cleanup_releases
----

== Crontab automatique

Si le projet contient `config/cron/crontab`, il est installé automatiquement lors du déploiement.

=== Variables disponibles dans le template

[cols="1,2,2"]
|===
| Variable | Description | Exemple

| `{{APP_HOME}}`
| Répertoire home de l'application
| `/home/mon-app--staging`

| `{{APP_FULL_NAME}}`
| Nom complet app--env
| `mon-app--staging`

| `{{MARTEN_ENV}}`
| Environnement Marten
| `staging`
|===

=== Exemple `config/cron/crontab`

[source]
----
# Récap quotidien à 7h
0 7 * * * cd {{APP_HOME}}/current && MARTEN_ENV={{MARTEN_ENV}} ./bin/{{APP_FULL_NAME}} recap_quotidien >> {{APP_HOME}}/shared/log/cron.log 2>&1
----

=== Idempotence

Pour les projets Marten, la commande `bin/marten install_cron` est utilisée.
Elle compare le crontab actuel avec le nouveau contenu et ne réinstalle que si différent.
Si le fichier `config/cron/crontab` n'existe pas, un message informatif est affiché et le déploiement continue.

=== Commande CLI Marten

Ajouter dans votre projet :

[source,crystal]
----
class InstallCron < Marten::CLI::Command
  command_name :install_cron
  help "Installe le crontab depuis config/cron/crontab."
  # ...
end
----

deploy appelle cette commande avec les variables d'environnement `APP_HOME`, `APP_FULL_NAME` et `MARTEN_ENV`.

== Arrêt gracieux (zero-downtime)

Lors de chaque déploiement, le script envoie `SIGTERM` au processus en cours et attend
qu'il se termine proprement avant de basculer vers la nouvelle release.
Les requêtes HTTP en cours ne sont pas interrompues.

Le timeout d'attente est configurable via la variable d'environnement `GRACEFUL_TIMEOUT`
(défaut : 30 secondes). Au-delà, un `SIGKILL` est envoyé en dernier recours.

*Kemal :*

[source,crystal]
----
Signal::TERM.trap do
  STDERR.puts "[SHUTDOWN] SIGTERM reçu — arrêt gracieux en cours..."
  spawn { Kemal.stop rescue nil }
end
----

*Marten :* l'arrêt gracieux est géré nativement par `Marten::Server`.

== Rollback

[source,sh]
----
bin/deploy rollback --production
----

Pour Marten, les migrations sont ré-appliquées sur la release précédente après le rollback.

== Structure sur le serveur

[source]
----
/home/mon-app--staging/
├── releases/
│   ├── 20260410_143022/          ← release horodatée
│   │   ├── bin/mon-app--staging
│   │   └── ...
│   └── 20260409_091500/
├── current -> releases/20260410_143022/
└── shared/
    ├── .env                      ← persistant entre les déploiements
    ├── env_exports.sh            ← exports générés par Crystal
    ├── nginx.conf                ← généré par init
    ├── repo.git/                 ← dépôt bare (fetch incrémental)
    ├── public/
    │   └── erreur-indisponible.html
    └── log/
        └── cron.log

/tmp/.mon-app--staging.pid        ← pidfile
/tmp/.mon-app--staging.sock       ← socket Unix (deploy:www 660)

/usr/local/etc/rc.d/mon_app__staging
/usr/local/bin/mon-app--staging -> current/bin/...
----

== NGINX

Le fichier `shared/nginx.conf` est généré lors de l'`init`.
Il est automatiquement lié selon le mode détecté :

[cols="1,2,2"]
|===
| Mode | Lien créé | Directive dans nginx.conf principal

| Passenger (`/opt/websites/`)
| `/opt/websites/mon-app--staging.conf`
| `include /opt/websites/*.conf;`

| pkg FreeBSD
| `sites-enabled/mon-app--staging`
| `include sites-enabled/*;`
|===

Le socket Unix est créé avec les permissions `deploy:www 660` pour que NGINX puisse y accéder.

== Gestion des fichiers de configuration

[cols="2,3,1"]
|===
| Fichier | Rôle | Versionné

| `config/deploy.yml`
| **Source unique de vérité pour l'infrastructure.** Environnements, hôtes, branches, URLs, framework.
| **Oui**

| `.env` local
| **Secrets du développeur.** Clés API DNS (OVH/Gandi) pour l'administration depuis la machine locale.
| **Non**

| `shared/.env` (serveur)
| **Secrets de l'application.** Construit lors de l'`init`. Identifiants DB, clés secrètes, SMTP.
| **Non**
|===

[WARNING]
====
Ne dupliquez jamais les informations de `config/deploy.yml` dans votre `.env` local.
====

== Configuration DNS (optionnel)

Registrars supportés : **OVH** et **Gandi**.

[source,sh]
----
bin/deploy dns-setup --staging   # Configure les clés API du registrar
----

Les enregistrements CNAME sont créés automatiquement lors du `init`.

=== Champs DNS optionnels par environnement

[source,yaml]
----
environments:
  staging:
    dns_subdomain: staging.mon-app    # sous-domaine (défaut : premier label de app_url)
    dns_target: serveur.example.com.  # cible CNAME (défaut : host avec point final)
----

== GitHub Actions (CI/CD)

[source,sh]
----
bin/deploy generate-ci
----

Génère `.github/workflows/deploy.yml` avec :

. **Job test** : PostgreSQL, Crystal, compilation + specs
. **Job deploy** : déploiement automatique sur push (staging / production)
. Notifications GitHub Issues en cas d'échec

=== Configuration

. Générer une clé SSH dédiée et l'autoriser sur le serveur
. Ajouter le secret `SSH_PRIVATE_KEY` dans les paramètres GitHub du dépôt
. Lancer `bin/deploy generate-ci` et commiter le workflow

== Variables d'environnement

=== Gérées automatiquement (skip par défaut)

Ces variables sont injectées par deploy et ne sont jamais demandées lors du `init` :

* `MARTEN_ENV`, `MARTEN_ALLOWED_HOSTS`, `MARTEN_SOCKET`
* `APP_HOST`, `APP_PORT`, `PORT`
* `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_NAME_TEST`
* `DATABASE_URL`

=== Variables personnalisées

Déclarées dans `env_vars.required` de `config/deploy.yml` :

[source,yaml]
----
env_vars:
  required:
    - key: SECRET_KEY
      secret: true
      generate: hex64     # auto-généré si vide
    - key: STRIPE_SECRET_KEY
      secret: true
----
