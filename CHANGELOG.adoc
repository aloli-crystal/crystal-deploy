== v0.1.15 — 2026-05-02

=== Fixed

* **Regression: `bin/deploy -v` triggered a deployment.** Since v0.1.12
  (`deploy` becoming the implicit default command), passing `-v` or
  `--version` alone was treated as an env flag and fell through to
  `command = "deploy"` → unwanted deployment on the current branch.
+
Fix: `--version` / `-v` is now filtered at the very top of `CLI#run`,
BEFORE any business logic (same level as `--help` / `-h`). USAGE
updated to explicitly list the meta flags.

* **`Deploy::VERSION` was out of sync.** The constant reported `0.1.0`
  while `shard.yml` was at `0.1.14`. Now read at compile time from
  `shard.yml` via a Crystal macro `{{ \`grep ...\` }}` → single
  source of truth, no drift possible.

== v0.1.14 — 2026-05-02

=== Added

* **`config/deploy.yml`: `opal_assets: true` compiles Opal at deploy.**
  Projects following the Aloli Opal convention (sources in `src/opal/`,
  output in `public/js/app.js`) can now delegate compilation to the
  shard instead of versioning the generated JS.
+
[source,yaml]
----
opal_assets: true   # default false (backwards-compat)
----
+
The shard runs, in the freshly cloned release, `bin/build-assets` if
present (convention from `aloli/les-amis-de-joseph`), otherwise
falls back to `OPAL_PREFORK_DISABLE=1 opal --compile -Isrc/opal
src/opal/application.rb > public/js/app.js`. The step is inserted
*between `link_shared` and `shards_prepare`* — no dependency on the
application binary, and the JS is ready before `start_service`.
+
*Server prerequisite*: `opal` (Ruby gem) installed. Otherwise, an
explicit error log is printed with the recommended `gem install opal`.

== v0.1.13 — 2026-05-02

=== Added

* **`config/deploy.yml`: `seed: false` disables the seed step.**
  For stateless apps (no database, no bootstrap data), `run_seed` can
  now be skipped via:
+
[source,yaml]
----
seed: false   # default true (backwards-compat)
----
+
The shard forwards the value to the remote script as a new positional
argument `$12 = SEED_ENABLED`; `run_seed()` short-circuits with
`return 0` and a log line when the flag is `false`.

=== Fixed

* **Secret leak in service rc.d startup log.** The `_log_env` function
  of the generated rc.d used `sed` with *basic* regex alternation
  (`\|`) which does NOT work on BSD sed (FreeBSD, macOS) — `\|` is
  treated as a literal `|` there. As a result, NO `PASSWORD|SECRET|
  TOKEN|KEY|PASS` pattern was ever matched, and every value appeared
  in plain text in the application log at startup.
+
Fix: `sed -E` (extended regex) with unescaped `|`. The regex now
works on both BSD and GNU sed. Patterns covered: `PASSWORD`,
`SECRET`, `TOKEN`, `API_KEY`, `APP_PASSWORD`, `PASS`.
+
*Recommended action*: rotate any secret that may have been exposed
in `~/<app>/shared/log/<app>.log` on the server.

=== Changed

* **Better rc.d startup failure diagnostic.** When the pidfile is
  present but the socket is missing after 15 s (typical case: the app
  crashed at bind, or doesn't listen on `UNIX_SOCKET`), the rc.d now
  prints the issue explicitly AND the last 30 lines of the
  application log. Same treatment when the pidfile stays missing.

== v0.1.12 — 2026-05-01

=== Changed

* **`deploy` is now the implicit default command.** Invoking the
  binary without a command name is equivalent to `deploy`:
+
  * `bin/deploy` → deploys to the current git branch's environment
    (auto-detection).
  * `bin/deploy --production` → deploys to `--production`.
+
Previously, an empty invocation just printed the help message.
Help is now printed only when `config/deploy.yml` does not exist
in the current directory (new-project bootstrap path) or when
`--help` / `-h` is explicitly passed. The `config/deploy.yml`
template is still generated in that case.

=== Documentation

* `Deploy::CLI.resolve_command(args)` extracted as a pure public
  method with 4 new specs covering the possible variants.
* USAGE refreshed: dedicated paragraph for the default case,
  examples reordered (shortest form first).

== v0.1.11 — 2026-04-30

=== Fixed

* **`init_env`: remote `.env` is now rewritten when a new payload is
  sent.** Before, as soon as a `.env` existed on the server,
  `init_env` printed *"kept as-is"* and ignored the incoming
  `ENV_B64`. Effect: variables auto-injected by `init` on the Crystal
  side (`APP_URL`, `UNIX_SOCKET`, `MARTEN_*`) never reached the
  server, and NGINX kept using the placeholder
  `<app>--<env>.example.app`.

  New semantics:

  ** `ENV_B64` non-empty → write the `.env` (after backing the old
     one up at `~/<app>/shared/.env.YYYYMMDD-HHMMSS.bak`).
  ** `ENV_B64` empty *and* `.env` present → kept as-is (the "No"
     path added in v0.1.10).
  ** `ENV_B64` empty *and* `.env` missing → clear warning "rerun
     init from your terminal".

== v0.1.10 — 2026-04-30

=== Changed

* **`n` at the final confirmation no longer aborts init.**
  Previously, answering `n` to *Confirm and send to server?* would
  `return` from the dialogue, skipping every remaining server-side
  step.

  `n` now means: *"don't touch the existing remote `.env`, but the
  server init continues normally"* (NGINX, bare repo, rc.d, system
  user, etc.). The SSH runner is invoked with `env_b64=""`; the
  remote script keeps the existing `.env`.

* **`n` at *re-configure required variables* now propagates intent.**
  If the user chooses to keep existing required variables, the
  optional-variables dialogue and the database dialogue are skipped
  too. Existing DB variables (`DB_USER`, `DB_PASSWORD`, `DB_NAME`,
  `DB_HOST`) are kept as-is from the remote `.env`. A single `n`
  at the start is therefore enough to mean "leave everything
  alone".

== v0.1.9 — 2026-04-30

=== Fixed

* **Kemal: `app_url` from `config/deploy.yml` is now honoured.**
  The shard only read the `APP_URL` variable from the remote `.env`
  to build the nginx `server_name` and the *Site available: ...*
  log line. But `init` never wrote that variable: every Kemal
  deployment fell back to the placeholder
  `<app>--<env>.example.app`.

  `init` now auto-injects two variables on Kemal projects (mirroring
  the Marten side):

  ** `APP_URL` ← `environments.<env>.app_url`
  ** `UNIX_SOCKET` ← `/tmp/.<app>--<env>.sock`

=== Documentation

* `Init.kemal_auto_vars(app_url, socket_path)` extracted as a pure
  public method with 2 new specs.

== v0.1.8 — 2026-04-30

=== Changed

* **Three-way confirmation in `init`: Y / n / r.** The final prompt
  *Confirm and send to server?* now offers three answers:
** *Y* (default, Enter) → send the configuration to the server.
** *n* → cancel the send and end the dialogue cleanly (`return 0`,
   no error), no replay.
** *r* → restart the prompt from scratch to fix a value.
+
Refines the v0.1.7 behaviour where *n* always restarted the dialogue.
Unknown answers print a hint and re-ask.

=== Documentation

* `Init.parse_confirm_choice` extracted as a pure public method with
  5 new specs (yes / no / retry variants, Enter default, unknown
  input → nil).

== v0.1.7 — 2026-04-30

=== Fixed

* **`init` summary: SMTP_PASS now masked.** Secret detection covered
  `password` but not bare `pass`, so `SMTP_PASS` was printed in clear
  at the summary stage. The `pass` pattern is now recognised, on top
  of `key`, `secret`, `token`. `STRIPE_PUBLISHABLE_KEY` keeps its
  explicit exception (it's public).

=== Changed

* **`init` no longer quits when the user refuses to send.** Replying
  "no" to *Confirm and send to server?* used to trigger a hard
  `exit 0`. The dialogue now loops back to the input + summary stage,
  letting the operator fix a value without restarting from scratch.
  `Ctrl-C` is still available to abort.
* **`init` shortcut on re-init.** When a remote configuration already
  exists and every required variable is already set on the server,
  the user is first asked *Do you want to re-enter the required
  variables? [y/N]*. Default No → all current values are preserved
  without prompting; only variables missing from the server get
  asked. Yes → unchanged v0.1.5 behaviour (per-variable prompt with
  "Enter = keep current").

== v0.1.6 — 2026-04-30

=== Fixed

* **`init`: robust bare-clone setup.** `init_repo()` no longer trusts
  the bare `[ -d "${REPO_DIR}" ]` test: it now uses
  `git rev-parse --is-bare-repository` to confirm the directory is an
  actual git repo. If a previous init left an empty/partial directory
  (failed clone, missing SSH key, wrong URL…), we wipe and re-clone
  instead of falling through to `git fetch`, which used to crash with
  *fatal: not a git repository*.
* If `git clone --bare` fails, the empty directory is cleaned up so the
  next `init` is not trapped by its own "already present" guard.

== v0.1.5 — 2026-04-30

  `init` reads `~/<app>/shared/.env` from the server. For each required
  variable, the prompt now displays `(Enter = keep current)` whenever a
  value already exists; pressing Enter keeps the current value. Avoids
  re-typing SMTP password, SECRET_KEY, etc. on every re-init.

=== Fixed

* **README** : `shard.yml` integration example corrected (entry point

== v0.1.0 — 2026-04-11

First public release.

=== Features

* **SSH deployment** from the local terminal — no server-side dependency
* **Frameworks**: native Marten and Kemal support via `framework` in `deploy.yml`
* **Capistrano-style layout**: `releases/`, `current/`, `shared/`
* **FreeBSD rc.d**: dynamic service script generation (`daemon(8)`, auto-restart, `REQUIRE: postgresql`)
* **nginx.conf**: dynamic generation (FreeBSD pkg mode or Passenger) with custom error pages (502/503/504)
* **Interactive dialog** to build the `.env` file during initialization
* **Databases**: automatic user and database creation (PostgreSQL, MariaDB, SQLite)
* **Automatic DNS**: CNAME creation via the OVH or Gandi REST API
* **One-command rollback** (including re-application of Marten migrations)
* **Retention** of the last N releases (configurable)
* **tmux compilation**: resilient to SSH disconnections
* **CI/CD**: automatic GitHub Actions workflow generation via `generate-ci`
* **Graceful shutdown** (zero-downtime): SIGTERM and wait for in-flight requests before cut-over
* **Automatic environment detection** from the current git branch
* **Prefix shortcuts**: `--stag` → staging, `--prod` → production
* **Automatic crontab**: idempotent installation from `config/cron/crontab`
* **Parallel deployment**: migrations, seed, assets and crontab run while the app compiles
* **Template variables**: `{{APP_HOME}}`, `{{APP_FULL_NAME}}`, `{{MARTEN_ENV}}`

=== Commands

[cols="1,3"]
|===
| Command | Description

| `init --<env>`
| Server initialization (run once, idempotent)

| `deploy --<env>`
| Deploy a new release

| `deploy` (without `--<env>`)
| Detect the environment from the current git branch

| `rollback --<env>`
| Roll back to the previous release

| `status --<env>`
| Active version and available releases

| `generate-ci`
| Generate the GitHub Actions workflow

| `dns-setup --<env>`
| Configure the DNS registrar credentials (OVH / Gandi)
|===

=== Supported databases

* PostgreSQL (Unix socket or TCP)
* MariaDB / MySQL
* SQLite
* None (`database: none`)

=== Supported DNS registrars

* OVH (3-key API)
* Gandi (Personal Access Token)

=== Languages

Automatic detection from `LANG`. English fallback.

* French, English, Spanish, German, Portuguese, Italian, Dutch

=== Deployment flow

[source]
----
clone_repo → link_shared → shards_prepare
→ compile_start (background)
  ├── run_migrations
  ├── run_seed
  ├── collect_assets
  └── install_crontab
→ compile_wait (synchronization)
→ activate_release → init_rcd → start_service → reload_nginx → cleanup
----
