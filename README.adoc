= crystal-deploy
:toc: left
:toc-title: Table of Contents
:toclevels: 3
:source-highlighter: rouge
:icons: font

Crystal shard for deploying https://kemalcr.com[Kemal] and https://martenframework.com[Marten] applications on POSIX servers (Linux, FreeBSD, etc.).
Capistrano style: `releases/`, `current/`, `shared/`.
Dynamically generates `rc.d` / systemd and `nginx.conf` scripts.

== Features

* SSH deployment from your local terminal — no server-side dependencies
* Native support for **Marten** and **Kemal** via the `framework` field in `deploy.yml`
* Capistrano structure: `releases/`, `current/`, `shared/`
* Dynamic generation of `rc.d` scripts (with `daemon(8)`, auto-restart and `REQUIRE: postgresql` dependency)
* Dynamic generation of `nginx.conf` (FreeBSD pkg or Passenger in `/opt`) with **custom error pages** (502/503/504)
* Interactive dialogue to build `.env` during initialization
* Automatic creation of PostgreSQL/MariaDB databases and users
* Automatic CNAME creation via OVH or Gandi API (keys read from `.env`)
* One-command rollback (with Marten migrations re-application)
* Keeps the last N releases (configurable)
* Crystal compilation inside a `tmux` session (resilient to SSH drops)
* Automatic generation of GitHub Actions workflow (CI/CD) via `generate-ci`
* **Graceful shutdown** (zero-downtime): SIGTERM + waits for requests to finish before switching

== Installation

Add the shard to your `shard.yml`:

[source,yaml]
----
dependencies:
  crystal-deploy:
    github: aloli-crystal/crystal-deploy
    branch: developpement
----

Then compile the `deploy` binary:

[source,sh]
----
shards install
crystal build lib/crystal-deploy/src/deploy.cr --release -o bin/deploy
----

Add `bin/deploy` to your `.gitignore` if you do not wish to version the binary.

NOTE: The `deploy` binary must be compiled in your project (not in the shard). It reads `config/deploy.yml` from the current directory.

== Configuration

Copy the example file to your project:

[source,sh]
----
# For a Marten project
cp lib/crystal-deploy/examples/marten/config/deploy.yml config/deploy.yml
----

Then adapt `config/deploy.yml`:

[source,yaml]
----
app_name: my-app                               # <1>
repo_url: git@github.com:user/my-app.git
crystal_main: src/server.cr
keep_releases: 10

# Crystal framework used: marten | kemal (default: kemal)
framework: marten                              # <2>

# Database adapter: postgresql | mariadb | mysql | sqlite | none
database: postgresql                           # <3>

# DNS registrar (optional — remove if no automatic DNS management)
dns:
  registrar: ovh                               # <4>
  zone: example.app

environments:
  development:
    branch: developpement
    host: deploy.example.com
    user: deploy
    app_url: https://dev.my-app.example.app
    dns_subdomain: dev.my-app                  # <5>
    dns_target: deploy.example.com.

  production:
    branch: production
    host: prod.example.com
    user: deploy
    app_url: https://my-app.example.app
----
<1> Used to name directories, services, and binaries: `my-app--development`
<2> Accepted values: `marten` or `kemal`. Adapts NGINX, migrations, CI, and `.env` variables
<3> Interactive database setup during `init`
<4> Accepted values: `ovh` or `gandi`.
<5> Optional — requires API keys in your local `.env` (see DNS section)

== Support: Marten vs Kemal

The `framework` field in `config/deploy.yml` automatically adapts the shard's behavior:

[cols="2,3,3"]
|===
| Behavior | `framework: kemal` | `framework: marten`

| NGINX `.env` variables
| `APP_URL` + `UNIX_SOCKET`
| `MARTEN_ALLOWED_HOSTS` + `MARTEN_SOCKET`

| NGINX Assets
| `/css/`, `/js/`, `/images/`, `/vendor/`
| `/assets/` → `public/assets/`

| Migrations
| `db/schema_pg.sql` at init
| `marten migrate` before each activation

| Rollback migrations
| Not applicable
| `marten migrate` on the previous release

| CI Tests
| `DATABASE_URL` + `schema_pg.sql`
| `DB_*` + `MARTEN_ENV=test` + `marten migrate`

| Seed
| `./bin/<app> seed`
| `./bin/<app> seed` (if command present)
|===

== Usage

=== Generating GitHub Actions workflow

[source,sh]
----
bin/deploy generate-ci
----

This command generates `.github/workflows/deploy.yml`, a complete workflow that:

. Runs tests on every push (adapted to the framework)
. Automatically deploys to development on every push to the `developpement` branch
. Automatically deploys to production on every push to the `production` branch

=== Server initialization (once)

[source,sh]
----
bin/deploy init --development
bin/deploy init --production
----

This command:

. Checks SSH connection
. Offers an interactive dialogue to configure DNS (optional, keys read from `.env`)
. Builds the `.env` file interactively
. On the server: creates the `deploy` user, directories, `.env`, and `nginx.conf`

=== Deployment

[source,sh]
----
bin/deploy deploy --development
bin/deploy deploy --production
----

Each deployment:

. Clones the branch into `releases/<timestamp>/`
. Links `shared/.env` and `shared/log/`
. Compiles the Crystal binary in `--release` mode (inside `tmux` if available)
. **Marten only**: applies migrations (`marten migrate`)
. **Graceful shutdown** of the old version (SIGTERM + waits for requests to finish)
. Switches the `current` link to the new release
. Installs/updates the `rc.d` script
. Starts the new version
. Reloads NGINX
. Deletes old releases (beyond `keep_releases`)

=== Graceful shutdown (zero-downtime)

During each deployment, the script sends `SIGTERM` to the running process and waits
for it to finish properly before switching to the new release.
In-flight HTTP requests are not interrupted.

The wait timeout is configurable via the `GRACEFUL_TIMEOUT` environment variable
(default: 30 seconds). Beyond that, a `SIGKILL` is sent as a last resort.

For the application to benefit from graceful shutdown, it must intercept `SIGTERM`.

*Kemal:*

[source,crystal]
----
Signal::TERM.trap do
  STDERR.puts "[SHUTDOWN] SIGTERM received — graceful shutdown in progress..."
  spawn { Kemal.stop rescue nil }
end
----

*Marten:* graceful shutdown is natively handled by `Marten::Server`.

=== Rollback

[source,sh]
----
bin/deploy rollback --production
----

For Marten, migrations are re-applied to the previous release after the rollback.

=== Status

[source,sh]
----
bin/deploy status --development
----

== Server Structure

[source]
----
/home/my-app--development/
├── releases/
│   ├── 20260304_143022/          ← timestamped release
│   │   ├── bin/my-app--development
│   │   └── ...
│   └── 20260301_091500/
├── current -> releases/20260304_143022/
└── shared/
    ├── .env                      ← persistent across deploys
    ├── nginx.conf                ← generated by init
    ├── public/
    │   └── erreur-indisponible.html ← custom error page (generated by init)
    └── log/

/tmp/.my-app--development.pid     ← pidfile
/tmp/.my-app--development.sock    ← Unix socket (deploy:www 660)

/usr/local/etc/rc.d/my-app--development
/usr/local/bin/my-app--development -> current/bin/...
----

== NGINX

The `shared/nginx.conf` file is generated during `init`.
It is automatically linked according to the detected mode:

[cols="1,2,2"]
|===
| Mode | Link created | Directive to add in main nginx.conf

| Passenger (`/opt/websites/` present)
| `/opt/websites/my-app--development.conf`
| `include /opt/websites/*.conf;`

| FreeBSD pkg
| `sites-enabled/my-app--development`
| `include sites-enabled/*;`
|===

The Unix socket is created with `deploy:www 660` permissions so that NGINX
(running under the `www` user) can access it.

== Configuration Files Management

The shard's architecture relies on a strict separation of responsibilities between configuration files. It is crucial to understand the role of each:

[cols="2,3,1"]
|===
| File | Role | Versioned

| `config/deploy.yml`
| **Single source of truth for infrastructure.** Contains the definition of environments (hosts, branches, URLs, DNS subdomains, framework used).
| **Yes**

| Local `.env`
| **Developer secrets.** Contains access keys to external APIs (like OVH or Gandi API) needed from the local machine to manage the infrastructure. Should never contain server configuration.
| **No**

| `shared/.env` (server)
| **Production application secrets.** Built interactively during `init`. Contains database credentials, Marten/Kemal secret keys, and SMTP credentials. Read only by the application on the server.
| **No**
|===

[WARNING]
====
**Never** duplicate information from `config/deploy.yml` (like URLs or hosts) in your local `.env`. The `deploy` binary reads the YAML file directly to orchestrate deployments.
====

== DNS Configuration (optional)

The shard can automatically create the DNS CNAME during initialization using the REST API of your registrar.

=== Supported Registrars

* **OVH**: Requires 3 keys (`OVH_APP_KEY`, `OVH_APP_SECRET`, `OVH_CONSUMER_KEY`)
* **Gandi**: Requires 1 key (`GANDI_PAT` - Personal Access Token)

Keys are read from your **local `.env`** file. If they are missing, the interactive dialogue will ask for them during `init` and automatically save them in your local `.env`.

[IMPORTANT]
====
Make sure `.env` is in your `.gitignore`:

[source,sh]
----
echo ".env" >> .gitignore
----
====

== GitHub Actions (Automatic CI/CD)

The `generate-ci` command automatically generates the workflow file adapted to your configuration and framework.

=== Step 1 — Generate a dedicated SSH key

[source,sh]
----
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/deploy_ed25519 -N ""
# Authorize the public key on the server
ssh-copy-id -i ~/.ssh/deploy_ed25519.pub deploy@your-server.net
----

=== Step 2 — Configure GitHub secrets

In your GitHub repository settings → *Settings → Secrets and variables → Actions*:

[cols="1,3"]
|===
| Secret | Value

| `SSH_PRIVATE_KEY`
| Content of `~/.ssh/deploy_ed25519` (private key)
|===

=== Step 3 — Generate the workflow

[source,sh]
----
bin/deploy generate-ci
git add .github/workflows/deploy.yml
git commit -m "ci: add automatic deployment workflow"
git push
----

The generated workflow automatically triggers a deployment on every push to the `developpement` (pre-production) and `production` branches.
