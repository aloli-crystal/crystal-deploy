== v0.1.5 — 2026-04-30

=== Ajouté

* **`init` préserve les variables déjà saisies.** Avant le dialogue,
  `init` lit `~/<app>/shared/.env` sur le serveur. Pour chaque variable
  obligatoire, l'invite affiche désormais `(Entrée = conserver l'actuel)`
  quand une valeur existe déjà ; taper Entrée garde la valeur courante.
  Évite de re-saisir mot de passe SMTP, SECRET_KEY, etc. à chaque
  re-init.

=== Corrigé

* **README** : exemple d'intégration `shard.yml` corrigé (point d'entrée
  `lib/deploy/src/cli.cr` au lieu de `lib/deploy/src/deploy.cr` qui
  produisait un binaire muet, et pinning `version: "~> 0.1"` au lieu de
  `branch: main` qui n'existe pas).

== v0.1.4 — 2026-04-29

=== Modifié

* **Module interne renommé** `CrystalDeploy` → `Deploy` (convention
  Aloli : retrait du préfixe `Crystal` sur les modules internes).
* Dossier source `src/crystal_deploy/` → `src/deploy/` (et le dossier
  spec correspondant). Chemins `require` internes adaptés.
* **Points d'entrée restructurés** pour s'aligner sur le reste de
  l'écosystème Aloli :
** `src/deploy.cr` devient le point d'entrée **bibliothèque** (charge
   tous les modules `Deploy::*`).
** `src/cli.cr` est le nouveau point d'entrée **binaire** (one-liner
   qui charge la bibliothèque et appelle `Deploy::CLI.run(ARGV)`).
** `shard.yml` `targets.deploy.main` pointe désormais sur
   `src/cli.cr`. La compilation produit toujours `bin/deploy` ; côté
   consommateur, la bibliothèque n'exécute plus la CLI comme
   effet de bord sur `require "deploy"` (bug précédent corrigé).
* Comportement et surface CLI inchangés.

== v0.1.3 — 2026-04-29

=== Modifié

* **Repo GitHub renommé** `aloli-crystal/deploy` → `aloli-crystal/deploy`
  (convention de nommage Aloli : les créations originales abandonnent
  le préfixe `crystal-`). Les anciens liens redirigent automatiquement.
* Champ `name:` du `shard.yml` mis à jour de `deploy` à `deploy`.
* **Cible de compilation renommée** de `deploy` à `deploy`
  (annule le renommage de v0.1.2 — la nouvelle convention de l'écosystème
  supprime aussi le préfixe sur les binaires). La compilation utilise
  désormais `shards build deploy` et produit à nouveau `bin/deploy`.

== v0.1.2 — 2026-04-22

* Renommage de la cible de compilation de `deploy` vers `deploy`
  pour cohérence avec l'écosystème. La compilation utilise désormais
  `shards build deploy` et produit `bin/deploy`
  (précédemment `bin/deploy`). Les appelants qui invoquent le binaire
  par son chemin doivent s'adapter ; aucun changement fonctionnel.

== v0.1.0 — 2026-04-11

Première version publique.

=== Fonctionnalités

* **Déploiement SSH** depuis le terminal local — aucune dépendance côté serveur
* **Frameworks** : support natif Marten et Kemal via `framework` dans `deploy.yml`
* **Structure Capistrano** : `releases/`, `current/`, `shared/`
* **rc.d FreeBSD** : génération dynamique du script de service (`daemon(8)`, redémarrage auto, `REQUIRE: postgresql`)
* **nginx.conf** : génération dynamique (mode pkg FreeBSD ou Passenger) avec pages d'erreur personnalisées (502/503/504)
* **Dialogue interactif** pour construire le `.env` lors de l'initialisation
* **Base de données** : création automatique utilisateur + base (PostgreSQL, MariaDB, SQLite)
* **DNS automatique** : création CNAME via API REST OVH ou Gandi
* **Rollback** en une commande (avec ré-application des migrations Marten)
* **Conservation** des N dernières releases (configurable)
* **Compilation tmux** : résistante aux coupures SSH
* **CI/CD** : génération automatique du workflow GitHub Actions via `generate-ci`
* **Arrêt gracieux** (zero-downtime) : SIGTERM + attente de fin des requêtes avant bascule
* **Détection automatique** de l'environnement depuis la branche git courante
* **Raccourcis par préfixe** : `--stag` → staging, `--prod` → production
* **Crontab automatique** : installation idempotente depuis `config/cron/crontab`
* **Déploiement parallélisé** : migrations, seed, assets et crontab s'exécutent pendant la compilation
* **Variables de template** : `{{APP_HOME}}`, `{{APP_FULL_NAME}}`, `{{MARTEN_ENV}}`

=== Commandes

[cols="1,3"]
|===
| Commande | Description

| `init --<env>`
| Initialisation du serveur (une seule fois, idempotente)

| `deploy --<env>`
| Déploiement d'une nouvelle release

| `deploy` (sans `--<env>`)
| Détecte l'environnement depuis la branche git courante

| `rollback --<env>`
| Retour à la release précédente

| `status --<env>`
| Version active et releases disponibles

| `generate-ci`
| Génère le workflow GitHub Actions

| `dns-setup --<env>`
| Configure les clés DNS du registrar (OVH / Gandi)
|===

=== Bases de données supportées

* PostgreSQL (dialogue socket Unix ou TCP)
* MariaDB / MySQL
* SQLite
* Aucune (`database: none`)

=== DNS supportés

* OVH (3 clés API)
* Gandi (Personal Access Token)

=== Langues

Détection automatique depuis `LANG`. Fallback anglais.

* Français, Anglais, Espagnol, Allemand, Portugais, Italien, Néerlandais

=== Flow de déploiement

[source]
----
clone_repo → link_shared → shards_prepare
→ compile_start (arrière-plan)
  ├── run_migrations
  ├── run_seed
  ├── collect_assets
  └── install_crontab
→ compile_wait (synchronisation)
→ activate_release → init_rcd → start_service → reload_nginx → cleanup
----
