== v0.1.10 — 2026-04-30

=== Modifié

* **« Non » à la confirmation finale n'arrête plus l'init.**
  Auparavant, répondre `n` à *Confirmer et envoyer sur le serveur ?*
  faisait `return` du dialogue : aucune autre étape côté serveur
  n'était exécutée.

  Le sens de `n` est désormais : *« ne touchez pas au `.env` existant,
  mais l'init du serveur continue normalement »* (NGINX, dépôt bare,
  rc.d, user système, etc.). Le runner SSH est appelé avec
  `env_b64=""` ; le script distant détecte le cas et conserve le
  `.env` existant.

* **« Non » à *re-configurer les obligatoires* propage l'intention.**
  Si l'utilisateur choisit de conserver les variables obligatoires
  existantes, le dialogue *Voulez-vous configurer les variables
  optionnelles depuis .env.example ?* et le dialogue base de
  données ne sont plus posés non plus. Les variables DB existantes
  (`DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_HOST`) sont reprises
  telles quelles depuis le `.env` distant. Un seul Non en début
  suffit donc à signaler « je ne touche à rien ».

== v0.1.9 — 2026-04-30

=== Corrigé

* **Kemal : `app_url` du `config/deploy.yml` désormais respecté.**
  Le shard ne consultait que la variable `APP_URL` du `.env` distant
  pour fabriquer le `server_name` nginx et le message
  *Site disponible : ...*. Or `init` ne posait pas cette variable :
  les déploiements Kemal retombaient systématiquement sur l'URL de
  démonstration `<app>--<env>.example.app`.

  `init` injecte maintenant automatiquement deux variables côté Kemal
  (équivalent du `inject_marten_vars` côté Marten) :

  ** `APP_URL` ← `environments.<env>.app_url`
  ** `UNIX_SOCKET` ← `/tmp/.<app>--<env>.sock`

=== Documentation

* `Init.kemal_auto_vars(app_url, socket_path)` extrait en méthode
  publique pure et testée (2 nouveaux specs).

== v0.1.8 — 2026-04-30

=== Modifié

* **Confirmation `init` tripartite : O / n / r.** L'invite finale
  *Confirmer et envoyer sur le serveur ?* propose désormais trois
  réponses :
** *O* (défaut, Entrée) → envoie la configuration sur le serveur.
** *n* → annule l'envoi et termine proprement le dialogue
   (return 0, aucune erreur), sans rejouer la saisie.
** *r* → reprend la saisie depuis le début pour corriger une valeur.
+
Affine le comportement v0.1.7 où *n* relançait toujours le dialogue.
Une saisie inconnue affiche un message d'aide et redemande.

=== Documentation

* `Init.parse_confirm_choice` extrait en méthode publique pure et
  testée (5 nouveaux specs : variantes oui / non / retry, Entrée par
  défaut, entrée non reconnue → nil).

== v0.1.7 — 2026-04-30

=== Corrigé

* **Récapitulatif `init` : SMTP_PASS masqué.** La détection des secrets
  englobait `password` mais pas `pass` seul ; `SMTP_PASS` était donc
  affiché en clair au récapitulatif. Le pattern `pass` est désormais
  reconnu, ainsi que toute occurrence de `key`, `secret`, `token`.
  Une exception explicite reste pour `STRIPE_PUBLISHABLE_KEY` (publique).

=== Modifié

* **`init` ne quitte plus si l'utilisateur refuse l'envoi.** Auparavant,
  répondre « non » à *Confirmer et envoyer sur le serveur ?* déclenchait
  un `exit 0` brut. Le dialogue boucle désormais sur la saisie + récap,
  permettant de corriger une valeur sans tout recommencer. `Ctrl-C`
  reste disponible pour abandonner.
* **`init` : raccourci en re-init.** Lorsqu'une configuration distante
  existe déjà et que toutes les variables obligatoires sont déjà
  définies sur le serveur, l'utilisateur reçoit d'abord l'invite
  *Voulez-vous re-configurer les variables obligatoires ? [o/N]*.
  Réponse Non (défaut) → toutes les valeurs courantes sont conservées
  sans nouvelle saisie ; les variables non encore définies sont les
  seules demandées. Réponse Oui → comportement v0.1.5 inchangé
  (saisie individuelle avec proposition de conserver chaque valeur).

== v0.1.6 — 2026-04-30

=== Corrigé

* **`init` : robustesse du clone bare.** `init_repo()` ne se contentait
  plus du test `[ -d "${REPO_DIR}" ]` : il vérifie via
  `git rev-parse --is-bare-repository` que le dossier est un vrai dépôt
  git. Si un init précédent a laissé un dossier vide ou partiel (clone
  échoué, clé SSH manquante, URL fautive…), on nettoie et on re-clone
  proprement au lieu d'enchaîner sur un `git fetch` qui plantait avec
  *fatal : pas dans un répertoire git*.
* En cas d'échec du `git clone --bare`, le répertoire vide est nettoyé
  pour que le prochain `init` ne soit pas piégé par sa propre garde
  « déjà présent ».

== v0.1.5 — 2026-04-30

* **`init` préserve les variables déjà saisies.** Avant le dialogue,

  obligatoire, l'invite affiche désormais `(Entrée = conserver l'actuel)`
  quand une valeur existe déjà ; taper Entrée garde la valeur courante.
  Évite de re-saisir mot de passe SMTP, SECRET_KEY, etc. à chaque
  re-init.

=== Corrigé

* **README** : exemple d'intégration `shard.yml` corrigé (point d'entrée
  `lib/deploy/src/cli.cr` au lieu de `lib/deploy/src/deploy.cr` qui
  produisait un binaire muet, et pinning `version: "~> 0.1"` au lieu de
  `branch: main` qui n'existe pas).

== v0.1.4 — 2026-04-29

=== Modifié

* **Module interne renommé** `CrystalDeploy` → `Deploy` (convention
  Aloli : retrait du préfixe `Crystal` sur les modules internes).
* Dossier source `src/crystal_deploy/` → `src/deploy/` (et le dossier
  spec correspondant). Chemins `require` internes adaptés.
* **Points d'entrée restructurés** pour s'aligner sur le reste de
  l'écosystème Aloli :
** `src/deploy.cr` devient le point d'entrée **bibliothèque** (charge
   tous les modules `Deploy::*`).
** `src/cli.cr` est le nouveau point d'entrée **binaire** (one-liner
   qui charge la bibliothèque et appelle `Deploy::CLI.run(ARGV)`).
** `shard.yml` `targets.deploy.main` pointe désormais sur
   `src/cli.cr`. La compilation produit toujours `bin/deploy` ; côté
   consommateur, la bibliothèque n'exécute plus la CLI comme
   effet de bord sur `require "deploy"` (bug précédent corrigé).
* Comportement et surface CLI inchangés.

== v0.1.0 — 2026-04-11

Première version publique.

=== Fonctionnalités

* **Déploiement SSH** depuis le terminal local — aucune dépendance côté serveur
* **Frameworks** : support natif Marten et Kemal via `framework` dans `deploy.yml`
* **Structure Capistrano** : `releases/`, `current/`, `shared/`
* **rc.d FreeBSD** : génération dynamique du script de service (`daemon(8)`, redémarrage auto, `REQUIRE: postgresql`)
* **nginx.conf** : génération dynamique (mode pkg FreeBSD ou Passenger) avec pages d'erreur personnalisées (502/503/504)
* **Dialogue interactif** pour construire le `.env` lors de l'initialisation
* **Base de données** : création automatique utilisateur + base (PostgreSQL, MariaDB, SQLite)
* **DNS automatique** : création CNAME via API REST OVH ou Gandi
* **Rollback** en une commande (avec ré-application des migrations Marten)
* **Conservation** des N dernières releases (configurable)
* **Compilation tmux** : résistante aux coupures SSH
* **CI/CD** : génération automatique du workflow GitHub Actions via `generate-ci`
* **Arrêt gracieux** (zero-downtime) : SIGTERM + attente de fin des requêtes avant bascule
* **Détection automatique** de l'environnement depuis la branche git courante
* **Raccourcis par préfixe** : `--stag` → staging, `--prod` → production
* **Crontab automatique** : installation idempotente depuis `config/cron/crontab`
* **Déploiement parallélisé** : migrations, seed, assets et crontab s'exécutent pendant la compilation
* **Variables de template** : `{{APP_HOME}}`, `{{APP_FULL_NAME}}`, `{{MARTEN_ENV}}`

=== Commandes

[cols="1,3"]
|===
| Commande | Description

| `init --<env>`
| Initialisation du serveur (une seule fois, idempotente)

| `deploy --<env>`
| Déploiement d'une nouvelle release

| `deploy` (sans `--<env>`)
| Détecte l'environnement depuis la branche git courante

| `rollback --<env>`
| Retour à la release précédente

| `status --<env>`
| Version active et releases disponibles

| `generate-ci`
| Génère le workflow GitHub Actions

| `dns-setup --<env>`
| Configure les clés DNS du registrar (OVH / Gandi)
|===

=== Bases de données supportées

* PostgreSQL (dialogue socket Unix ou TCP)
* MariaDB / MySQL
* SQLite
* Aucune (`database: none`)

=== DNS supportés

* OVH (3 clés API)
* Gandi (Personal Access Token)

=== Langues

Détection automatique depuis `LANG`. Fallback anglais.

* Français, Anglais, Espagnol, Allemand, Portugais, Italien, Néerlandais

=== Flow de déploiement

[source]
----
clone_repo → link_shared → shards_prepare
→ compile_start (arrière-plan)
  ├── run_migrations
  ├── run_seed
  ├── collect_assets
  └── install_crontab
→ compile_wait (synchronisation)
→ activate_release → init_rcd → start_service → reload_nginx → cleanup
----
